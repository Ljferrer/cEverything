## Context — the gap / problem

Hermes v0.22.2 serves JSON-RPC 2.0 over WebSocket at `ws://127.0.0.1:9119/api/ws` from `hermes serve` / `hermes dashboard`, with events `message.start/delta/complete`, `reasoning.delta`, `thinking.delta`, `reasoning.available`, `tool.start{tool_id,name,args}`, `tool.complete{tool_id,name,summary,inline_diff}`, `session.info`, `sessions.changed`, and methods `session.active_list`, `session.resume`, `session.history`, `session.create`, `prompt.submit{session_id,text}`, `session.branch{session_id,name}` (fork; the source keeps running) (verified: `tui_gateway/contracts/events.py`, `sessions.py`, `prompt_voice.py` at `59ee4989`, read via plan 1's evidence block). Event frames are `{jsonrpc:'2.0', method:'event', params:{type, session_id, seq, payload}}`, and `session.active_list` reports one of `idle|starting|waiting|working|streaming|resuming` per session, with `parent_session_id` on branched sessions (verified: `tui_gateway/ws.py` and `contracts/sessions.py` at `59ee4989`, read via plan 1's evidence block).

On a loopback bind the socket accepts `?token=` pinned by `HERMES_DASHBOARD_SESSION_TOKEN`, and the upgrade handler checks Host and Origin, so only a process on the laptop can connect: the relay is the single Hermes client and a headset never is (verified: `hermes_cli/web_server_boundary.py` at `43b6acbe`, read via plan 1's evidence block). The HTTP API server's `POST /api/sessions/{id}/fork` ends the source session as `branched`, unlike `session.branch` (verified: `gateway/platforms/api_server.py` at `59ee4989`, read via plan 1's evidence block). Thinking and tool events reach the wire only when the host config has `display.show_reasoning: true` and `display.tool_progress: true` and the model emits reasoning (verified: lane `bighelp-protocol` reading `tui_gateway`, read via plan 1's evidence block; gate names medium confidence).

Plan 1 lands the relay, the protocol validators, the source and command loaders, the per-session slab cache `relay.slabs.get(sid)`, `--record <file>`, and the `canEdit` gate; it starts `hermes` by default and falls back to `synthetic` when no source starts (verified: `plan1-final-for-agents.md` Task 1, read at draft time). No Hermes host runs on this machine at draft time (verified: `command -v hermes` empty and port 9119 closed on 2026-10-17), so the tests use a fake gateway and every host-shape detail is either verified at source or tagged [assumed: the shapes read at `59ee4989` hold for the installed v0.22.2 — if wrong: one mapper row changes]. The demo needs Hermes traffic even when the operator has no session open, and a recording must stand in when the live host is down (user).

## Pivotal constraints

- Hermes stays bound to `127.0.0.1:9119` with a fixed `HERMES_DASHBOARD_SESSION_TOKEN`; a public bind requires an auth provider and `--insecure` is a no-op (verified: `hermes_cli/subcommands/dashboard.py` at `59ee4989`, read via plan 1's evidence block).
- The relay's CLI and loaders are plan 1's files (PIN-22): `--seed`, `--replay`, and `--fast` are read by the source modules from `process.argv`, never added to `server/relay.mjs` (user: plans stay file-disjoint); this holds only because the relay ignores argv flags it does not own (plan 1 Task 1 amendment; A10).
- Build window from 3 PM to 5:15 PM; each task fits one worker in 90 minutes; tests run with no Hermes installed, against a fake gateway on an ephemeral port (user).
- A live host at the 5:30 PM Quest slot is the goal; a recording made before the slot is the fallback, and the room must read REPLAY while it plays (PIN-5) (user).
- The protocol shapes in plan 1's Task 1 are the contract; every frame this plan emits passes `isServerEvent` from `shared/protocol.mjs`, except the one-shot `{t:'mode', mode:'replay'}` signal from `replay.mjs`, which the relay consumes as a mode update and never broadcasts raw: the relay composes every outbound `mode` frame with the client's `canEdit` (verified: plan 1 Task 1; the mode-composition rule is a plan 1 Task 1 amendment, A8).

## New domain terms · Recommended ADRs

Recording (the JSONL plan 1's `--record` writes), seed session (a session the relay created so the demo has traffic), fast replay (`--fast`, every gap 10 ms). ADRs: none.

## Commander's Intent

- **Purpose:** every session on the operator's Hermes host stands in the room as a live obelisk, a recording of that host stands in when it is down, and a word typed on the laptop or a pinch in the headset reaches Hermes as `prompt.submit` or `session.branch` through the relay.
- **Method:** one `hermes.mjs` source speaks JSON-RPC to the loopback gateway and normalizes its events to plan 1's protocol, attaching every session it learns of; one `replay.mjs` source re-emits a recording under `mode:'replay'`; three command modules translate `say`, `fork`, and `pipe` into `prompt.submit` and `session.branch` through the owning source's `sendCommand`, and refuse when the owner cannot write.
- **Mechanism latitude:** the JSON-RPC client shape (hand-rolled over `ws` or a small helper), the slab id scheme, the seed prompt wording, the replay default file path and the fast gap, the history-seeding depth, the fake-gateway fixture layout, and whether `hermes.mjs` also hands its sender to the relay-supplied `sendCommand` argument are implementer's choice; substituting any of these mechanisms while the End states and binding guardrails hold is not a plan deviation and warrants no issue.
- **Binding guardrails:** headsets never talk to Hermes; `hermes.mjs` holds the one authenticated loopback socket and sends `client.capabilities {server_requests:true}` (PIN-9) · fork is WebSocket `session.branch`, never the HTTP `/fork` route (PIN-10) · a harness is one source module, every `session` event carries `harness:'hermes'`, and nothing in this plan touches `src/` (PIN-19) · only the eight files listed under Tasks 1 and 2 change; plan 1's files and other plans' files are never edited (PIN-22) · replay emits `mode:'replay'` and never re-broadcasts a recorded `mode` frame (PIN-5) · `HERMES_DASHBOARD_SESSION_TOKEN` is read only under `server/` · every emitted frame is a plan 1 protocol shape, the one-shot replay `mode` signal excepted (the relay composes the outbound `mode` frame, A8).
