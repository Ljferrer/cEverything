## Context — the gap / problem

Tool calls are the most frequent visible act in an agent session, and PIN-2 makes them the room's motion: a projectile flies from the calling slab to a fixed pylon and the pylon glows, so a viewer can tell which agents are browsing, editing files, or running shells without reading a slab (user; verified: plan 1 D2 at `/Users/ljf/GitHub/cEverything/.claude/worktrees/hermes-vr-spatial-5b5bf8/docs/plans/2026-10-17-obelisks-1-foundation.md`). Hermes emits `tool.start{name,args}` and `tool.complete{name,summary,inline_diff}`, and plan 2's source maps them to the protocol's `tool` frame (verified: `tui_gateway/contracts/events.py` at `59ee4989`, read via plan 1's evidence block). Claude Code transcripts carry `tool_use{id,name,input}` and `tool_result` blocks with names such as `Bash`, `Read`, `Edit`, `WebFetch`, `WebSearch`, `Workflow`, `Skill`, and `mcp__*`, and plan 3's source maps them to the same `tool` frame (verified: this session's transcript, read via plan 1's evidence block).

The wire frame is `{t:'tool', sid, id, name, phase:'start'|'complete', args, summary, diff}`; `src/net.js` re-emits every server frame on `bus` as `new CustomEvent(frame.t, {detail: frame})`, and `src/main.js` calls each feature's `install({scene, camera, renderer, bus, net, onFrame})`, where `onFrame(cb)` runs `cb(dt, now)` inside `renderer.setAnimationLoop` on every render, including immersive sessions (verified: plan 1 Task 1 plan slice at `/Users/ljf/GitHub/cEverything/.claude/worktrees/hermes-vr-spatial-5b5bf8/docs/plans/2026-10-17-obelisks-1-foundation.md`). `src/features/room.js` exports `getObelisk(sid)`, which returns the obelisk's `THREE.Object3D` carrying `setState`, `setBeacon`, and `slabMesh(slabId)`, and `allObelisks()`; each slab mesh carries `userData {sid, slabId}` and each base `userData {sid, kind:'base'}` (verified: plan 1 Task 2 plan slice at `/Users/ljf/GitHub/cEverything/.claude/worktrees/hermes-vr-spatial-5b5bf8/docs/plans/2026-10-17-obelisks-1-foundation.md`). `fixtures/synthetic.jsonl` carries one `start`/`complete` tool pair per pylon (`web_search`; `write_file` with `args.path` on its start and a unified `diff` on its `complete`; `terminal`), each `start` paired with a role-`tool` slab of the same `id`, one `tool` frame for a sid no session declares, and one `Agent` start (verified: plan 1 Task 1 plan slice at `/Users/ljf/GitHub/cEverything/.claude/worktrees/hermes-vr-spatial-5b5bf8/docs/plans/2026-10-17-obelisks-1-foundation.md`, amended today). The client never branches on harness name, so the pylon map keys on tool names alone and holds both harnesses' names in one table (verified: plan 1 D19 at `/Users/ljf/GitHub/cEverything/.claude/worktrees/hermes-vr-spatial-5b5bf8/docs/plans/2026-10-17-obelisks-1-foundation.md`). Tool frames reach the wire only when the Hermes host runs with `display.tool_progress: true` (verified: lane `bighelp-protocol`, read via plan 1's evidence block; gate name medium confidence). Judges score "It works in space" and "It clicks fast", and a projectile crossing the room is the quickest visible proof that the feed is live (verified: moltenhack.com `#tracks`, read via plan 1's evidence block).

## New domain terms · Recommended ADRs

Glow (the pylon's 2 s lit state from a tool start), spawning tool (a tool name that creates an agent and fires no projectile: `Agent`, `Workflow`, `Task`). Pylon and projectile are defined in plan 1. ADRs: none.

## Commander's Intent

- **Purpose:** every non-spawning tool call in the room is visible as motion: a projectile from the calling slab to the tool's pylon and a glow on the pylon from the moment the call starts, so a viewer tells at a glance which agents are browsing, editing files, or running shells.
- **Method:** one pure name-to-pylon table shared by both harnesses; four fixed wireframe pylons at the compass points; a pooled projectile along a quadratic curve on each `tool` start, ticked by plan 1's `onFrame`; a 2 s glow from the start frame; the filesystem pylon's path and `+n/-m` on `complete`; frames for unknown sessions and for spawning tools are dropped.
- **Mechanism latitude:** the sphere geometry and size, the curve's lift height, the clock source for the tween, how the glow is rendered (emissive on a `MeshStandardMaterial`, or a color and opacity pulse on the wireframe material), the troika label parameters, how the base mesh is found under the obelisk (a `traverse` for `userData.kind === 'base'` or a direct child lookup), the shape of the fake `THREE` stubs in the pool test, the projectile color source (`colorFor('tool')` from `src/colors.js` or a constant), and the `+n/-m` label format are implementer's choice; substituting any of these mechanisms while the End states and binding guardrails hold is not a plan deviation and warrants no issue.
- **Binding guardrails:** fixed pylons on the room edge, a projectile from slab to pylon, a glow on the pylon, no avatars (PIN-2) · wireframe look only (PIN-8) · the client never branches on harness name; the map keys on tool names only (PIN-19) · no edit to any plan 1 file or any other plan's file; this plan adds only its five files (PIN-22) · `src/pylon-map.js` and `src/projectile.js` import nothing from `three`; only `pylons.js` adds objects to the scene; the pure tests run under `node --test` (PIN-56).
