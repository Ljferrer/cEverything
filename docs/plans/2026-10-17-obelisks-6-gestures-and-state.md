## Context — the gap / problem

Fork and pipe are the two creation acts of the demo: pinch an obelisk base with nothing foreign selected and a sibling obelisk rises; select a slab in obelisk A, then pinch obelisk B's base, and B receives `From <A title>: <slab text>` (user). The relay half lives in plans 1 and 2: the protocol fixes `{t:'fork', sid}` and `{t:'pipe', from, to, slab}` and `shared/protocol.mjs` exports `isClientCommand(o)` for them (verified: plan 1 Task 1 slice, `docs/plans/2026-10-17-obelisks-1-foundation.md` at `2f37f30`); plan 2's `fork.mjs` calls `session.branch` (the source session keeps running), its `pipe.mjs` reads the slab text and delegates to `say`, and a target whose owner cannot write answers `{t:'error', text:'read-only harness'}` (verified: plan 2 D6, D34, and Task 2 slice, `docs/plans/2026-10-17-obelisks-2-hermes-harness.md` at `2f37f30`; `tui_gateway/contracts/sessions.py` at `59ee4989` via plan 1's evidence block). Nothing on the client yet turns a pinch into either command (verified: worktree at `2f37f30` holds no `src/` files).

Plan 1's `main.js` calls `install({scene, camera, renderer, bus, net, onFrame})` on every `src/features/*.js` in filename order, where `onFrame(cb)` runs `cb(dt, now)` inside `renderer.setAnimationLoop` on every render, immersive sessions included; `net.send(cmd)` writes to the relay, and every server event, including `mode {canEdit}` and `state {sid, status}`, is re-emitted on `bus` as a `CustomEvent` named by its `t` with the frame in `detail` (verified: plan 1 Task 1 slice at `2f37f30`). Plan 1's `xr.js` emits `select {sid, kind:'base'|'slab', slabId, object}`, `selectstart {sid}`, `selectend {sid}`, and `miss` the same way and sets `bus.selected` to the last selected obelisk and `bus.selectedSlab` to `{sid, slabId}` on a slab select (verified: plan 1 Task 3 slice at `2f37f30`); `laptop.js` does click-to-select through the same `hitToEvent` mapper (verified: plan 1 Task 3 slice at `2f37f30`) [assumed: `laptop.js` sets `bus.selectedSlab` like `xr.js` — if wrong: laptop clicks only fork]. Plan 1's `room.js` exports `getObelisk(sid)`, the obelisk `THREE.Object3D` carrying `setState(status)`, `setBeacon(on)`, and `slabMesh(slabId)`, plus `allObelisks()`; each base mesh carries `userData {sid, kind:'base'}`; `colors.js` exports `stateColor(status)` for the five statuses and `colorFor(role)` (verified: plan 1 Task 2 slice and End state 4 at `2f37f30`).

An obelisk that is waiting for a human must be findable across the room: waiting is yellow with a raised beacon that stays until the user selects that obelisk, working and streaming pulse, idle is dim, error is red (verified: plan 1 D18 / PIN-18 at `2f37f30`; prior art Claude Code Agent View and Hermes `derive_pet_state` via plan 1's evidence block). A client on the bare share link receives `canEdit:false` and the relay refuses its commands; the page must also ignore gestures that send commands so a viewer's pinch is inert (verified: plan 1 D23 / PIN-23 at `2f37f30`). The client never branches on harness name, so a fork aimed at a Claude Code obelisk is sent and refused by the relay, not filtered on the client (verified: plan 1 D19 / PIN-19 at `2f37f30`). A held pinch on an obelisk base is plan 5's hold-to-talk and also fires plan 1's `select`: plan 5's `voice.js` sets `bus.talking = sid` once a hold passes 300 ms and clears it on `selectend`, dispatches `talk {phase:'start'|'sent'|'dropped'|'error', sid}` (`start` at arming, before the 300 ms mark), and leaves the skip of that `select` to this plan (verified: plan 5 D60, D69, D76, and Task 1 slice, `docs/plans/2026-10-17-obelisks-5-voice.md` at `2f37f30`).

## Pivotal constraints

- File fence: this plan adds `src/gesture.js`, `src/gesture.test.mjs`, `src/features/fork.js`, `src/features/pipe.js`, `src/features/state.js` and edits nothing plan 1 or plans 2 through 5 own; features are picked up by `main.js`'s `import.meta.glob` with no loader edit (verified: plan 1 D17 and D22 at `2f37f30`).
- No command leaves a view-only client: both gesture features consult the last `mode` event before `net.send` (verified: plan 1 D23 at `2f37f30`).
- Headset behavior cannot run under `node --test`, so the decision logic is a pure module and the three features run under Node against a fake `bus` (an `EventTarget`) and a recording `net`; no test imports `room.js`, which pulls troika and the scene; only the in-scene look (the pipe line, the beacon mesh, the pulse as motion) is judged at audit_sha or at the Quest slot (user: no headset time spent building; verified: plan 1 D4 at `2f37f30`).
- Build window is from 3 PM to 5:15 PM with one worker; the one task fits that window (user).
- No DOM inside the immersive session: the pipe line and the beacon are scene meshes (verified: plan 1 pivotal constraints at `2f37f30`).

## Non-goals / deferred

In-scene toasts for relay `error` events (console only) · filtering fork or pipe by harness on the client (the relay refuses read-only targets) · undo or multi-slab pipe · drag or two-hand gestures · hand-tracking consent · beacon sound · a laptop-only gesture UI (laptop clicks flow through plan 1's `select` event, so fork works with a mouse and pipe does when A6 holds) · voice (plan 5) · pylons and projectiles (plan 4) · logging inbound commands in the relay (plan 1 owns `relay.mjs`).

## New domain terms · Recommended ADRs

Beacon (the raised marker plan 1's `setBeacon(true)` shows on a waiting obelisk), pipe line (the one-second line from a slab to the base it was piped into), gesture decision (the pure `decide` output: a `fork` command, a `pipe` command, or null), acknowledge (the base select that only lowers a raised beacon). ADRs: none.

## Commander's Intent

- **Purpose:** a pinch creates: pinch a base to fork that session, select a slab and pinch another base to pipe it there; and any session waiting for a human is visible across the room until someone picks it.
- **Method:** one pure decision function over plan 1's `select` event that returns the protocol command; two thin features that gate it on `canEdit`, `bus.talking`, the throttle, and a raised beacon, send it, log every send and suppression, and draw the feedback; one feature that maps `state` events onto plan 1's `setState` and `setBeacon` with a pure sticky-waiting rule and an `onFrame` pulse; every send path runs under `node --test` on a fake bus; nothing edits a plan 1 file; a view-only client sends nothing.
- **Mechanism latitude:** the pulse's easing and the material property it modulates, the pipe line's geometry and removal timer, the fork throttle's data structure, whether `pipe.js` imports `three` statically or inside the pipe handler, whether `getObelisk` is resolved at install or on first use, the exact wording after the `fork:` / `pipe:` prefix and the four reason words, and whether `session {status}` seeds the initial status beside `state` are implementer's choice; substituting any of these mechanisms while the End states and binding guardrails hold is not a plan deviation and warrants no issue.

## Notes / conscious deviations

- The fork-versus-talk rule lives in this plan: plan 5 publishes `bus.talking` (set once a hold passes 300 ms, cleared on `selectend`) and the `talk` events; `fork.js` and `pipe.js` skip a base `select` while `bus.talking` equals its sid (D76). The `talk {phase:'start'}` event is not a gate: plan 5 dispatches it at arming, before the 300 ms mark, so gating on it would also suppress the fork of a short pinch on an already selected obelisk, which plan 5 D61 keeps as a plain select.
- PIN-22 file ownership (the five plan 6 files are the whole footprint) is audited by the WAR plan-faithfulness seat; this plan carries no footprint End state.
- Every check forces `--test-reporter=tap`: Node 24's default reporter off a TTY is `spec`, whose summary reads `ℹ pass`, not `# pass`. The pattern `^ES<n>\b` keeps `ES1` from also running `ES10`, and the `^ *ok [0-9]+ - ES<n> ` line proves the named case ran, since a pattern that matches no test still prints `# pass 1` for the file.
- The beacon is sticky by the literal PIN-18 reading: it stays up through later `working` or `idle` events (the operator may have answered from the TUI) and lowers only on a `select` of that obelisk in VR or on the laptop; while it is up, the first base select only lowers it (D77).
- Vision Pro gestures are checked in the visionOS Simulator before 5:15 PM (plan 1 PIN-4) since the 2 PM Vision Pro slot precedes this plan's landing; the Quest slot from 5:30 PM to 6:30 PM is the only headset check.
- If plan 1's `room.js` already forwards `state` events to `setState`, the second call from `state.js` is idempotent; `state.js` owns the beacon, the pulse, and the steady color either way.
- The sibling obelisk rising and the `From <A title>:` slab are plan 2's replies and are checked at the 5 PM pre-flight (backstop row 1), not at audit_sha; this plan's End states stop at the sent frame, the cleared selection, and the in-scene state.
