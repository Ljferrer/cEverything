Reusable mechanics from WAR Phase 1 of the migration. The same shadow→bake→cleanup recipe repeats at the 3 remaining sites (consolidate, gather, fetch_extraction), so these are not one-offs.

**The shadow pattern (per-site swap recipe).** Each site first lands an *inert* call: `nr = normalize_extraction(ext['extraction_object'])` runs alongside the legacy parse and only emits a per-page `logger.warning` carrying the literal token `NORMALIZE_EXTRACTION_MISMATCH` when the new result diverges from legacy. HARD CONSTRAINT (a) = the shadow must not change behavior. Two deliberate choices that satisfy this and should be kept at the other sites (verify still present before acting):
- The shadow is **not** wrapped in try/except — it leans entirely on the module's documented "Never raises" contract (`layers/llm_helpers/extraction_helpers.py`). If a future PyUtils pin regressed that contract, an unguarded shadow would *crash* the handler — i.e. the inert step would change behavior. Acceptable at this sha because the contract is explicit + tested (PR-A/PR-B), but it is the single point where the shadow's inertness depends on an external submodule pin. If ever defending it: `try: ... except Exception: logger.warning('..._SHADOW_ERROR ...')`, PHI-free (pk + flag only).
- The shadow log line is PHI-free and bounded by page count (one WARNING per per-page mismatch) — keep it pk+flag only.

**Reachability is per-handler SYMLINKS, not `add_layers` (corrects the plan/red-team premise).** The deduplicate handler (and siblings) are **container-image Lambdas** whose `Dockerfile` does `COPY *.py`; shared `llm_helpers`/`boto_helpers` modules reach the bundle only as **per-file symlinks committed in the handler dir** (e.g. `message_utils.py -> ../../../../utils/layers/llm_helpers/message_utils.py`, tracked as git mode `120000`). A NEW shared module is therefore NOT importable just because it sits in the layer dir — **each consuming handler dir needs its own symlink.** C1 shipped `from extraction_helpers import normalize_extraction` without the symlink → the deduplicate Lambda crashed on dev at module load (`Runtime.ImportModuleError: No module named 'extraction_helpers'`); fixed by adding the symlink (PR #157). **Correction for D0/E0:** consolidate + gather most likely do NOT need an `add_layers` change — they need the same `extraction_helpers.py` symlink in their handler dirs (verify each handler's Dockerfile/symlink set first). `fetch_extraction` lives in `llm_helpers` itself, so it is already fine. The local gate can't catch this (no `cdk synth`/no deploy) — only the dev deploy surfaces it. (verify still present before acting.)

**The bake gate is infra, not code.** Promotion off Dev is gated on a **net-new** `aws_logs.MetricFilter` (the repo previously had NONE — ExecSummaryV3 uses code-published custom metrics, not log filters) keyed to the literal `"NORMALIZE_EXTRACTION_MISMATCH"` string on the consuming handler's `.log_group`, feeding a `cloudwatch.Alarm` (threshold=0, GREATER_THAN_THRESHOLD, NOT_BREACHING so it never false-fires on no-data; period=1h so it is human-paced, not sub-minute). The metric is intentionally **static / dimension-less** (`metric_value='1'`, no per-case dimensions) to stay cardinality-limited (the "Shadow noise" risk). **Order matters: the MetricFilter must be deployed before starting any site's dev bake**, else divergence is only raw log lines, not the alarm the plan relies on. `.log_group` on the `PythonFunction` is valid + synth-safe at the pinned `aws-cdk-lib==2.207.0` (requirements-dev.txt).

**Topology gotcha — one metric, two log groups.** `create_assistive_metadata_steps_v2` is invoked TWICE in `assistive_summary_stack.py` (once `name_mod='V2-Solo'`, once `name_mod=''` from the AssistiveIndexV3 builder). Construct IDs are `name_mod`-suffixed so there is no synth/logical-ID collision, but if both metadata SMs ever coexist in one stack, two MetricFilters on two distinct log groups publish to the *one shared* static metric and two alarms watch it — redundant but harmless, and actually the correct aggregate bake gate. In current `post_init` wiring only AssistiveIndexV3 is built, so production emits exactly one filter+alarm. (verify still present before acting.)

**Cross-cutting WAR gotcha — gate-audit stale-tip downgrade.** All three phase-1 gate-audits flagged the SAME thing: the gate-HEAD sha they ran against trailed the live integration tip (gates ran at `18c7c920` / `27d1eac3`; tip had advanced to `146115d6`). Per the stale-tip defusing rule, a gate output produced at a sha that is not the current integration tip CANNOT be a provably-unrun land-halt, so it is recorded **SOFT, never HARD** — even when the mapped file is byte-identical at both shas (which it was here). **Lesson for future WAR phases:** sequential tasks landing on one integration branch keep advancing the tip out from under earlier gates; to get a *confirmed* (not SOFT) pass, re-run the gate at the current integration tip (or rebase the task atop it) so gate-HEAD == tip. Not a defect — a structural artifact of one shared integration branch.
